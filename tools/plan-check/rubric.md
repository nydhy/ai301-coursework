# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause (its Diagnosis section) read against every control run and artifact in the repro-evidence block (or, live, the student's own posted repro comment). | Pass if the stated cause is consistent with everything the repro evidence actually shows, including every control run. Fail if the diagnosis contradicts or is silently inconsistent with a control run or artifact the repro evidence shows — a control that already rules the stated mechanism out (present where it shouldn't be, or absent where the diagnosis needs it present) fails this regardless of how confidently the diagnosis reads, and regardless of whether the diagnosis merely repeats a theory floated earlier in the thread. | required |
| scope-bounded | The plan's Scope/not-in-scope statement and its full list of proposed changes, read as one list, not file-by-file. | Pass if the plan commits to one bounded change mapping directly onto the issue's trigger, with any other observation explicitly deferred out of scope and a reason given. Fail if the proposed changes are several independent efforts (a redesign, a migration, a new abstraction layer, a version bump unrelated to the bug, a CI matrix, a UI rework) that the issue itself never asked for — bundling an unasked-for rewrite alongside the fix fails this even when the core fix inside the bundle is correct. | required |
| plan-executable | The plan's Files/areas and Approach sections. | Pass if the plan names concrete files or code locations and a concrete, ordered sequence of steps that a stranger could start executing immediately without asking the author anything. Fail if a real decision is deferred to build time ("somewhere", "upstream or vendored, whichever is easier", no chosen files or layer named, "investigate X" standing in for an actual approach). | required |
| test-plan-decisive | The plan's Test plan section, read against the repro evidence's own steps and artifacts. | Pass if the test plan names a specific, observable outcome tied to the repro evidence — re-running the exact repro steps/controls and naming the concrete expected result (an exit code, an output value, a named artifact) such that two different readers would agree whether it happened. Fail if the test plan names no observable outcome ("should feel fast", "nothing else should feel broken") or substitutes a generic action with no outcome specific to this fix ("run the full test suite" with nothing named about what in it proves the fix). | required |
| thread-and-conventions | The plan comment's text, read against (a) any maintainer comment in the thread highlights that already states a diagnosis, a fix location, or a rejected approach, and (b) the repo-facts block's stated AI-use/disclosure policy. | Pass if EITHER no maintainer in the thread has already given a direction the plan's approach would contradict, or the plan explicitly engages that direction (adopts it, or states why it diverges) rather than silently routing around it — AND the repo has no AI-disclosure requirement, or has one and the comment discloses. Fail if a maintainer already gave an explicit diagnosis/fix-location/direction in the thread and the plan comment's approach ignores it without engagement, or if the repo's stated policy requires disclosure and the comment does not disclose. | required |
| honest-unknowns | The plan's stated risks/unknowns (or their absence), and the plan comment's confidence language, read against what the diagnosis and test plan can actually promise. | Pass if genuine open questions or risks are named as such, or the plan explicitly states none remain given its narrow bounded scope. Never changes the verdict; reported for the record only. | preferred |

## Verdict rule

Accept if every `required` check (`diagnosis-grounded`, `scope-bounded`, `plan-executable`, `test-plan-decisive`, `thread-and-conventions`) grades `pass`. Any required check graded `fail` or `unclear` holds the package at `reject` — `unclear` is always treated as `fail`, since a plan this rubric cannot verify from the package is not ready to build from. `honest-unknowns` is preferred and never changes the verdict; it is reported for the record only.
