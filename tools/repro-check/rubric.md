# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment line (tool version/commit, OS/platform, install method), read against the issue's stated target version and the repo-facts bug-report template's asked-for fields. | Pass if the report names the tool's version (or an explicit commit/build) and the OS/platform actually used, AND if that version differs from the issue's stated target, the report says so explicitly (e.g. "issue filed against X, retested on Y"). Fail if no environment is given at all, or if a used version diverges from the issue's target with no acknowledgement of the deviation. | required |
| steps-followable | The repro report's steps, read as literal commands, code, or UI actions a stranger with no access to the reporter's machine could carry out. | Pass if every step is a literal, copyable command/snippet/action with enough starting state given to run it from scratch (files created inline, config shown, no unstated setup). Fail if a step is vague ("set up the project", "run the usual tests") or depends on a resource a stranger cannot get (a private repo, an unshared config file, a link only the author can open). | required |
| behavior-matches-issue | The artifact in the repro report (command output, log excerpt, error, screenshot description) compared line-by-line against the issue's own stated trigger and observed behavior. | Pass if EITHER (a) the artifact's trigger is the same operation/input the issue names (not a substituted syntax or altered input) and the observed result (error type, exit code, message, visual state) matches the issue's reported behavior rather than an adjacent one, OR (b) the report is an honest cannot-reproduce: a real attempt at the issue's actual trigger, with an artifact from that attempt, that names a specific difference (environment, version, data shape) plausibly explaining the non-reproduction. Fail if the report substitutes different input/syntax than the issue describes and narrates the result as confirming it, if the shown artifact is a different failure mode than the one reported (e.g. a graceful validation error narrated as the reported crash, or intact output narrated as the reported corruption/hang), or if no artifact ties to the issue's actual trigger at all. | required |
| honest-outcome | The report's stated conclusion (confirmed / partially confirmed / cannot-reproduce) compared to what its own shown artifacts actually demonstrate. | Pass if the conclusion claims no more than the artifacts shown support — including a cannot-reproduce that is stated as such rather than talked around. Fail if the report asserts confidence ("guaranteed reproducible", "verified the root cause", repeated-run certainty) that is not backed by a shown artifact, or draws a root-cause diagnosis the report never actually demonstrates. | required |
| claim-has-intent | The candidate claim comment's own sentences. | Pass if the claim comment names a concrete, specific next investigative step tied to the issue's actual mechanism (a function, file, dependency, or thread comment named in the issue). Fail if the comment is generic self-assignment boilerplate ("I'd like to work on this", "please assign to me", flattery about the project) with no specific next step, a "+1 also seeing this" with no stated intent, or an over-promised fix/timeline ("guaranteed fix in 2 days"). | required |
| ai-disclosure | The repo-facts contribution/AI-use policy field, compared against the text of the claim comment and (once posted) the repro comment. | Pass if EITHER the repo has no stated AI-use policy or a permissive one that does not require disclosure for this kind of comment, OR the policy requires disclosure and at least one of the comments contains an explicit disclosure naming AI assistance and that a human verified the work. Fail if the policy requires disclosure (unconditionally, or conditional on AI having been used) and no comment discloses. | required |
| control-run-present | Whether the repro report includes a second, contrasting run (a control) that isolates the variable the issue names, alongside the main reproduction. | Pass if a control/comparison run is present and its result is shown. Never changes the verdict either way when absent — many complete reports are terse and skip it. | preferred |

## Verdict rule

Accept if every `required` check grades `pass`. Any `required` check graded `fail` or `unclear` holds the package at `reject` — `unclear` is treated as `fail` throughout, since proof this rubric cannot verify is proof that is not ready to post. `preferred` checks never change the verdict; they are reported for the record only.

In live mode, claim-only drafts skip `behavior-matches-issue`, `honest-outcome`, and `control-run-present` (graded `unclear` / not yet applicable, per SKILL.md), and the verdict rule above applies only to the remaining required checks: `environment-recorded` is also skipped claim-only (it belongs to the repro report), leaving `claim-has-intent` and `ai-disclosure` (against the claim comment alone) to decide a claim-only verdict.
